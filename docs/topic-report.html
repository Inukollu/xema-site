report

Reports are what users run in Data Portal. Each report defines where it appears in the Data Portal menu, the filters it asks for, its SQL query and its column names. A built report counts calls without SQL.

The name and description are shown in the Data Portal menu. A clear description tells users what the report answers without opening it.

Owner and sharing

  • Owner is the user the report belongs to, who decides who else can run it.
  • A report can be run by its owner and by the users and roles it is shared with. A report that is not shared appears only in its owner's menu.
  • A report appears only for users who can run it, so a new report is not visible to anyone until it has an owner. Set an owner before the report is shared.
  • Changes to a report apply to everyone who runs it, the next time they open it.
  • Deleting a report removes it from Data Portal for everyone.

Menu placement

  • Group is the Data Portal menu section the report appears under. Reports are listed under their group, in the order of the Data Portal menu. The number beside a group heading is the number of reports in it.
  • Within a group, reports are sorted by Order in the group and then by name.

Output and filters

  • Table on screen shows the results in a table that can be sorted, filtered and exported as a spreadsheet.
  • Recordings on screen is the same table with playback and download for each call.
  • Call detail download is the standard call record download. It has its own date range and no other filters.
  • The selected filters are the fields Data Portal shows to the user running the report. Each filter fills a placeholder in the query. With no filters, the query runs as written.

Query

  • Write standard SQL. Use a filter's placeholder where its value belongs: {FromDate}, {ToDate}, {FromEpoch}, {ToEpoch}, {AgentUserName}, {PhoneId}, {ANI}, {DNI}.
  • {FromEpoch} and {ToEpoch} are the same dates in call ID form, which allows fast searches of the call tables.
  • {FromDate} and {ToDate} are both included in the report, so compare a date column with >= {FromDate} and <= {ToDate}. The epoch values mark the start and end of those days, so compare a call ID with >= {FromEpoch} and < {ToEpoch}.
  • Optional conditions are for filters that may be left blank. A condition is used only when its filter has a value. The conditions used are joined with AND and inserted where you write {WHERE}. If the query already has a WHERE clause, write {AND} before it; it becomes AND when there are conditions and is removed when there are none.
  • Add a limit to any query that could return a whole table.

Column names

  • Enter a display name for a column. Columns not listed keep the names the query returns.
  • For a call detail download, only the listed columns are included, in the listed order.

Testing

  • A report can be tested before it is saved. Xema shows the exact SQL that would run, with placeholders filled in and conditions applied, and a test run returns the first rows.
  • If the database rejects the query, its error message is shown.

Built reports

A built report counts calls without SQL. Choose what it counts (interactions, calls or agent calls) and the columns to group by, such as a queue, a disposition or a value set by a flow. Each group becomes a row with the figures available for that source, such as calls answered or average handling time. With no columns selected, the report lists every row with every column.

A filter keeps only the rows where the column has the given value, as shown in the report.

You own a built report, and only you can edit it. It counts calls in the processes you own, or all calls if your role covers every process. Share it from the reports list, and view it in Data Portal.
